## ЭТАП 2. Шаг 3: Чтение мыслей сервера (EXPLAIN ANALYZE)
Логика: Этот инструмент — рентген для вашего SQL-кода. Он показывает, как планировщик СУБД разбил ваш приказ на элементарные шаги и где именно захлебнулся процессор. Без него оптимизация — это гадание на кофейной гуще.
------------------------------
## 1. Архитектурный синтаксис (Запуск рентгена)
Мы подкладываем оператор EXPLAIN ANALYZE на самую первую строчку перед любым готовым SELECT, UPDATE или DELETE.

EXPLAIN ANALYZESELECT client_id, SUM(amount) FROM orders WHERE status = 'completed'GROUP BY client_id;


* Просто EXPLAIN: Показывает теоретический план — предположение сервера о затратах (cost). Базу данных реально не дергает.
* С надстройкой ANALYZE: Физически выполняет запрос на диске, замеряет точное время работы в миллисекундах и выводит фактическую карту боя.

------------------------------
## 2. Главные узлы чтения карты боя
При анализе вывода рентгена мы ищем две ключевые физические операции:

* Точка коллапса: Seq Scan (Sequential Scan)
Линейный, построчный перебор файлов на диске. Сервер читает таблицу целиком с начала до конца. Если это происходит на таблице в 10 000 000 строк — это критическая ошибка архитектуры (отсутствие индекса).
* Точка триумфа: Index Scan / Index Only Scan
Прыжок по скоростным рельсам. Сервер проигнорировал чтение таблицы и взял данные из каталога-указателя. Index Only Scan означает, что сервер вообще не ходил к файлу таблицы, забрав всё из памяти индекса.

------------------------------
## 3. Главные капканы планировщика

* Капкан №1: Слепота по времени (Execution time vs Planning time)
Иногда Planning time (время, потраченное сервером на размышления, как выполнить запрос) превышает само время выполнения Execution time. Это маркер того, что в запросе слишком много громоздких мостов (JOIN) или трехэтажных вложенных матрешек.
* Капкан №2: Вранье статистики (Rows vs Actual Rows)
Если планировщик думает, что фильтр вернет 10 строк (rows=10), а по факту прилетает миллион (actual rows=1000000), он выберет в корне неверную стратегию соединения таблиц (например, тяжелый цикличный Nested Loop вместо быстрого Hash Join).
* Щит защиты: Принудительное обновление карт статистики СУБД:
   
   ANALYZE orders; -- Обновляет информацию о распределении данных для планировщика.
